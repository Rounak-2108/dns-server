## Concepts Learned:- 

**Why did we start refactoring?**                                                                        -> Initially, almost the entire DNS resolver was written inside server.js.                               It is responsible for:                                                                                   * Receiving DNS requests                                                                                 * Parsing DNS packets                                                                                    * Checking the blocklists                                                                                * Managing cache                                                                                         * Forwarding requests to Google DNS                                                                      * Parsing response                                                                                       * Logging                                                                                                * Statistics                                                                                             * Dashboard                                                                                              This violated one of the most important software engineering principles:-"One file should have one primary responsibility."                                                                                 If every feature is inside one file:-                                                                    * debugging becomes difficult                                                                            * testing becomes difficult                                                                              * code becomes longer                                                                                    * adding new features becomes risky

**Goal of Day 11:-**                                                                                     Convert the DNS Resolver into multiple independent modules where each module has only one job. Instead of server.js->Everything    we changed it into                                                           server.js:                                                                                             -> dnsParser.js                                                                                          -> dnsForwarder.js                                                                                       -> cacheManager.js                                                                                       -> blocklist.js                                                                                          -> logger.js                                                                                             -> statsManager.js                                                                                       -> dashboard.js                                                                                          Now every module has its own responsibility.

**Refactoring the Blocklist:-**                                                                          Originally server.js was loading:-                                                                       * blocklist.txt                                                                                          * creating Set()                                                                                         * checking blocked domains                                                                               All of this was moved into  security/ blocklist.js                                                       Now server.js simply asks    *if(blocklist.isBlocked(domain))*   instead of worrying about how the blocklist works.                                                                                         *Benifit:-*                                                                                              The server only asks "Is this domain blocked?".  It doesn't care:                                        * where the data comes from                                                                              * how it is loaded                                                                                       * whether it uses a Set,Array or Database                                                                This hides implementation details.

**Refactoring Cache Manager:-**                                                                          All cache logic was moved into  cache/ cacheManager.js                                                   The cache manager becomes responsible for                                                                * get()                                                                                                  * set()                                                                                                  * remove()                                                                                               * cleanupExpired()                                                                                       * startCleanup()                                                                                         Instead of writing *cache[domain]* inside server.js, the server now simply writes *cacheManager.get(domain)*                                                                                                *Why?*                                                                                                   -> The server shouldn't know                                                                             * how cache is stored                                                                                    * whether it is an Object                                                                                * Map                                                                                                    * Redis                                                                                                  * Database                                                                                               It simply asks "Give me cached data."

**Why did we add getAll() (before cleanup refactoring)?**                                                -> Before cleanup was refactored, we discussed why a function like *getAll()* maybe useful.              *Reason:-* Cleanup needs to iterate over every cache entry. It must check                                * Has TTL expired?                                                                                       * Should it be deleted?                                                                                  * Should it remain?                                                                                      Instead of exposing the cache object directly, providing a method such as *getAll()* keeps cache access centralized and makes future changes easier.

**Refactoring DNS Forwarding:-**                                                                         Originally, server.js contained                                                                          client.send()                                                                                            client.on("message", ...)                                                                                client.close()                                                                                           Everything was inside one callback.                                                                      Now forwarding logic lives inside   forwarding/ dnsForwarder.js                                          Server.js only calls *await dnsForwarder.forward(msg)*                                                   *Benifit:-*                                                                                              The server no longer knows                                                                               * sockets                                                                                                * callbacks                                                                                              * networking                                                                                             It simply says "Forward this DNS request."

**Why use Promise?**                                                                                     -> A DNS request is asynchronous. When we send *client.send(...)*                                        Google DNS has not replied yet. So we cannot immediately return a response. Instead, the function returns a Promise. The Promise says "I don't have the answer yet" but "I promise to give it to you when Google replies."                                                                                         When Google replies *resolve(response)* means success. We received the DNS response.                     When forwarding fails *reject(error)* means Something went wrong. No DNS response was received.

**Why Async/Await?**                                                                                     -> Before                                                                                                client.on("message", () => {.....});                                                                     The program flow was broken. Reading the code required jumping inside callbacks. After refactoring       const response = await dnsForwarder.forward(msg);                                                        const answers = dnsParser.parseAnswer(response);                                                         cacheManager.set(...);                                                                                   server.send(...);                                                                                        The code now reads almost like English.                                                                  Forward->Wait->Parse->Cache->Reply                                                                       This makes the program much easier to understand and debug.

**Bug found during refactoring:-**                                                                       While converting to async/await,                                                                         a leftover line remained inside the try block                                                            logger.log(`Forwarding failed: ${err.message}`);                                                         This caused *Reference Error* -> err is not defined                                                      because                                                                                                  * the request had actually succeeded                                                                     * err only exists inside the catch block                                                                 The fix was simply to replace it with                                                                    logger.log("Response sent to client");

**Parsing Multiple DNS Answers:-**                                                                       Previously, we only extracted    const ip = [...]   from the response. Now  *dnsParser.js* contains      parseAnswers(response)   which loops through every Answer Record inside the DNS packet. Instead of extracting only one IPv4, it now returns  [{ type:"A", ttl:178, data:"142.251.xxx.xxx"}]    This makes the parser reusable.

**Why option B for parseAnswers() ?**                                                                    -> We discussed two designs.                                                                             *Option A*                                                                                               Parser returns only one IPv4 address.                                                                    return ip;                                                                                               *Option B*                                                                                               Parser returns every parsed record.                                                                      [{ type, ttl, data}]                                                                                     Server.js decides which record it wants.                                                                 *Advantages:-*                                                                                           * Parser becomes generic                                                                                 * Supports future record types.                                                                          * Easier to extend.                                                                                      * Closer to real DNS resolver.

**Seperation of Responsibilities:-**                                                                     -> After refactoring.                                                                                    server.js  Only controls the flow                                                                        Receive request->Check blocklist->check cache->Forward->Parse->Cache->Reply                              It no longer performs the internal work itself.                                                          *dnsForwarder.js* -> Only forwards DNS packets.                                                          *dnsParser.js* -> Only parses DNS packets.                                                               *cacheManager.js* -> Only manages cache.                                                                 *logger.js* -> Only stores log.                                                                          *blocklist.js* -> Only manages blocked domains.                                                          *statsManager.js* -> Only stores statistics.

**Biggest Lesson of Day 11:-**                                                                           Good software is not measured by how many lines of code you write. It is measured by how well responsibilities are seperated. A module should do one thing and do it well. This makes code:            * Easier to read                                                                                         * Easier to test                                                                                        * Easier to debug                                                                                        * Easier to extend                                                                                       * Easier for other developers to understand.                                                             This is exactly how real production backend systems are structured.


## INTERVIEW NOTES:- 

*Why did you refactor your DNS resolver?*
-> Initially, almost all the logic was inside server.js, making it long and difficult to maintain. I refactored the project by separating responsibilities into different modules such as the parser, cache manager, DNS forwarder, blocklist, logger, and stats manager. This made the code more readable, easier to debug, easier to extend, and closer to how production backend applications are structured.

*What software engineering principle did your refactoring follow?*
-> The refactoring mainly follows the Single Responsibility Principle (SRP). Every module is responsible for only one task. For Example:-                                                                         * dnsParser.js -> Parsing DNS packets                                                                    * cacheManager.js -> Managing cache                                                                      * dnsForwarder.js -> Forwarding DNS requests                                                             * blocklist.js -> Managing blocked domains                                                               * logger.js -> Logging                                                                                   * statsManager.js -> Statistics

*Why is seperating responsibilities important?*
-> Seperating responsibilites provides several benifits:                                                 * Easier debugging                                                                                       * Easier testing                                                                                         * Better readability                                                                                     * Easier feature additions                                                                               * Less risk of breaking unrelated code                                                                   * Better collaboration between developers 

*Why should server.js call cacheManager.get() instead of accessing the cache object directly?*
-> Because server.js should not know how the cache is implemented.                                       Today the cache is an Object.                                                                            Tomorrow it could become                                                                                 * Map                                                                                                    * Redis                                                                                                 * MongoDB                                                                                                Only cacheManager.js would change.                                                                       server.js would remain unchanged.

*Why is this better than exposing the cache object?*
-> It hides implementation details.The server simply asks: "Do you have this domain cached?" instead of knowing                                                                                                  * how data is stored                                                                                     * how expiration works                                                                                   * how deletion works 

*Why did you create a seperate dnsForwarder.js?*
-> Because forwarding DNS packets is a completely different responsibility than processing requests. The forwarder is only responsible for                                                                        * Sending DNS packets                                                                                    * waiting for Google's response                                                                          * returning that response                                                                                It knows nothing about                                                                                   * cache                                                                                                  * parsing                                                                                                * blocklist                                                                                              * dashboard

*What are the advantages of moving forwarding logic into a separate module?*
-> Advantages:-                                                                                          * Cleaning server.js                                                                                     * Easier debugging                                                                                       * Easier testing                                                                                         * Reusable forwarding logic                                                                              * Better maintainability

*Why does dnsForwarder.forward() return a Promise?*
-> Because DNS communication is asynchronous. After sending a packet to Google DNS, the response is not available immediately. The Promise represents a future value that will become available once Google sends the response.

*What does resolve(response) mean?*
-> It means the DNS query completed successfully and the response has been recieved from Google DNS.

*What does reject(error) mean?*
-> It means forwarding failed due to an error such as a socket failure or timeout.

*Why did you replace callbacks with async/await?*
-> Callbacks create nested code and make execution flow harder to follow.                                Async/await makes a asynchronous code look like synchronous code, improving readability and maintainability.

*What actually happens when Javascript reaches await?*
-> Execution of the async function pauses until the Promise settles. The event loop can continue executing other tasks while waiting. Once the promise resolves, execution resumes from the next line.

*Does await block the entire Node.js server?*
-> No. It only pauses the current async function. The Node.js event loop continues processing other incoming requests. This allows multiple DNS requests to be handled concurrently.

*Why did you create parseAnswers()?*
-> Previously the parser only extracted one IPv4 address. parseAnswers() makes the parser generic by parsing every answer record and returning structured information.

*Why did you choose Option B?*
-> Option B returns every parsed answer. The parser becomes generic. Server.js decides which records it wants to use. This design is much closer to a real DNS resolver.

*Why shouldn't the parser decide which record to cache?*
-> Because parsing and decision-making are different responsibilities.The parser should only interpret DNS packets.The server decides which records are useful for caching.

*During refactoring you encountered "err is not defined". Why?*
-> I accidently left.                                                                                    logger.log(err.message);                                                                                 inside the try block.                                                                                    Since err only exists inside the catch block, JavaScript threw a ReferenceErrorr.                        Removing that incorrect line fixed the issue.

*Why didn't the DNS request fail even though the error occurred?*
-> Because the response had already been                                                                 * parsed                                                                                                 * cached                                                                                                 * sent back to the client                                                                                The error happened afterward due to the incorrect log statement.

*If tomorrow you replace Google DNS with Cloudflare DNS, which file changes?*
-> Only the forwarding module or configuration file.The parser, cache, blocklist, dashboard, and statistics remain unchanged.This demonstrates good modular design.

*If tomorrow you replace the in-memory cache with Redis, which file changes?*
-> Only cacheManager.js.                                                                                 Server.js still uses                                                                                     * cacheManager.get()                                                                                    * cacheManager.set()                                                                                     * cacheManager.remove()                                                                                  No other module needs modification. 

*If tomorrow you add DNS-over-HTTPS support, which module would mostly change?*
-> The forwarding module. The parser, cache manager, blocklist, logger, and dashboard would remain almost unchanged.

*Which Day 11 refactoring improved your project the most?*
-> The biggest improvement was separating the forwarding logic into its own module and replacing callbacks with async/await.It made server.js much cleaner and easier to understand because it now focuses only on controlling the request flow instead of handling socket communication.

*If another developer joins your project, how will this refactoring help them?*
-> They don't need to understand the entire project at once.If they want to improve caching, they only need to study cacheManager.js.If they want to improve parsing, they only need dnsParser.js.This greatly reduces the learning curve.

*If your project grows to 20,000 lines of code, why is this architecture beneficial?*
-> Because every module has a clearly defined responsibility.Developers can work independently on different modules, making the project easier to maintain, test, and extend without affecting unrelated parts of the system.

*Why is returning a Promise considered better than passing callbacks around?*
-> Promises separate the producer of asynchronous work from its consumer. They improve composability, centralize error handling with try/catch when used with async/await, and avoid deeply nested callback structures ("callback hell"), making the code easier to read and maintain.

*Does async/await make asynchronous code synchronous?*
-> No.It only makes the syntax look synchronous.Under the hood, the operations are still asynchronous and are handled by Node.js's event loop and Promise mechanism.

*What design pattern does your DNS resolver now resemble?*
-> It resembles a layered, modular architecture where:                                                   * server.js acts as the orchestrator/controller.                                                         * Each module encapsulates one responsibility.                                                           * Modules communicate through well-defined interfaces rather than directly manipulating each other's internal data.                                                                                           This loose coupling makes the system easier to evolve over time.
