## Concepts Learned:-

**1. Why did we need Multiple DNS Servers?**                                                             -> Until Day 11, our DNS server forwarded every request to only one upstream DNS server (Google DNS).    Architecture:-  Client->My DNS Server->Google DNS                                                        *Problem:-*                                                                                              If Google DNS becomes unavailable:                                                                       * Internet Outage                                                                                        * Network issue                                                                                          * Timeout                                                                                                * Server Down                                                                                            Our DNS Server also fails because it has no backup server.                                               *Solution:-*                                                                                             Instead of using only one DNS server, maintain a list of DNS servers.                                    Client->My DNS Server = [Google DNS, Cloudflare DNS, Quad9 DNS]                                          If one server fails, automatically try the next one. This process is called Failover.

**2. Configuration Driven Design:-**                                                                     -> Earlier we had : Google_DNS_IP       Google_DNS_Port                                                  This only supports one DNS server.                                                                       We replaced it with:-  DNS_SERVERS: [{name: "Google DNS", ip: "8.8.8.8", port: 53}, {name: "Cloudflare DNS", ip: "1.1.1.1", port: 53}]                                                                          *Advantages:-*                                                                                           * Easy to add more DNS servers.                                                                          * No code changes required                                                                               * Better scalability                                                                                     * Cleaner architecture

**3. DNS Timeout:-**                                                                                     -> Suppose Google DNS never replies.                                                                     Without timeout:- Send request->Wait Forever->Client never gets a reply                                  So we introduced:- DNS_TIMEOUT: 2000                                                                     Meaning:- Wait only 2 seconds. If no reply arrives: Move to DNS server.

**4. Flow of a DNS Request:-**                                                                           Client->My DNS Server->Try Google DNS->Response?                                                         If yes:  Return response                                                                                 If no:  Timeout->Try Cloudflare->Response->Return response

**5. Why use await new Promise() ?**                                                                     -> Our sockets works with events. Example:-                                                              client.on("message", ...)                                                                                and                                                                                                      client.on("error", ...)                                                                                  These events happen later. But await only understands Promises. So we create:                            const response  = await new Promise((resolveAttempt) => {});                                             This Promise waits until:                                                                                * message                                                                                                * timeout                                                                                                * error                                                                                                  occurs.

**6. Why did we keep Inner Promise?**                                                                    -> Even after removing the outer Promise, we kept:                                                       await new Promise(...)                                                                                   Reason:- The socket API is event-based.                                                                  Without Promise:                                                                                         client.send(...); //Function immediately continues                                                       There is nothing for await to wait for.                                                                  Promise converts:                                                                                        Events->Promise->await                                                                                   This bridge is one of the most important JavaScript patterns.

**7. Outer Promise vs Inner Promise:-**                                                                  -> *Before Refactoring:-*                                                                                return new Promise(async (resolve, reject) => {});                                                       Purpose:- Represented the entire forwarding operation.                                                   Inside it:                                                                                               await new Promise(resolveAttempt => {});                                                                 Purpose:- Represented one DNS server attempt.                                                            *After Refactoring:-*                                                                                    We removed                                                                                         return new Promise(...)                                                                                  because async function already returns a Promise.                                                        But we kept:                                                                                             await new Promise(...)                                                                                   because socket events still need to be converted into a Promise. 

**8. Async/Await Mapping:-**                                                                             -> Old Promise API [ resolve(value) ] -> New Async/Await [ return value; ]                               Old Promise APi [ reject(error) ] -> New Async/Await [ throw error; ]

**9. Why client.send() doesn't mean success?**                                                           -> Many beginners think: client.send(...) means "Google replied."                                        Wrong.                                                                                                   It only means: "The packet has been sent."                                                               The reply comes:                                                                                         * immediately                                                                                            * after 50ms                                                                                             * after 1 second                                                                                         * never                                                                                                  That's why we wait for events.

**10. What Happens When DNS Server doesn't Respond?**                                                    ->  client.send()->Packet sent->No response->2 seconds->Timeout callback->resolveAttempt(null)->await finishes->response = null->Try next DNS Server

**11. Why did we use unfinished?**                                                                       -> Possible Scenario:- Timeout Fires       And       Response arrives almost simultaneously              Without Protection: Both callbacks execute.                                                              Problems:-                                                                                               * duplicate logs                                                                                         * multiple client.close()                                                                                * multiple resolveAttempt()                                                                              So we use:-                                                                                              let finished = false;                                                                                    Every callback begins with:                                                                              if(finished) return;                                                                                     finished = true;                                                                                         Only first callback proceeds.

**12. Failover Algorithm:-**                                                                             for each DNS server->send request->wait->response?->Yes->return reponse->No->next server->All failed?->throw error


## INTERVIEW NOTES:-

*Why did you store DNS servers in an array of objects instead of separate variables?*
-> I choose an array of objects because it is scalable and follows the Open/Closed Principle. If I need to add another DNS provider in the future, I simply append another object to the array without modifying the forwarding logic. This design is easier to maintain, easier to iterate over, and keeps the code independent of the number of upstream servers.

*Why didn't you use Array.forEach()?*
-> Because the failover logic depends on trying one server at a time. for...of works naturally with await, allowing sequential execution and early exit once a server responds successfully. Using forEach with asynchronous operations would make the control flow harder to manage and could start multiple requests unnecessarily.

*Why did you use setTimeout() instead of relying on client.on("error")?*
-> Because UDP is connectionless. If an upstream DNS server simply doesn't respond, the socket may never emit an error event. Therefore, the application must define its own timeout to determine when a request should be considered failed and when to try the next upstream server.

*Why did you call clearTimeout() after recieving the DNS response?*
-> The timeout is only used to detect when an upstream DNS server does not respond. Once a valid response is recieved, the timeout is no longer needed. Calling clearTimeout() prevents the timeout callback from executing later and accidentally closing the socket or rejecting a Promise that has already been resolved.

*Why did you store the timeout in config.js instead of hardcoding 2000?* 
-> I stored the timeout in config.js because it is a configurable parameter rather than application logic. Different environments may require different timeout values depending on network conditions. Keeping it in the configuration makes the system easier to maintain, test, and tune without modifying the application code.

*Why did you implement multiple upstream DNS Server?*
-> Initially, my DNS server forwarded every request to only one upstream DNS server, Google DNS. The problem with this approach is that if Google DNS becomes unavailable due to a timeout, network issue, or maintenance, my DNS server would also fail to resolve domains.                                         To make the DNS server more reliable, I implemented support for multiple upstream DNS servers. Now, if the first DNS server doesn't respond within the configured timeout, my server automatically forwards the request to the next available DNS server. This process is known as DNS failover and improves the availability and reliability of the DNS resolver.

*What is DNS Failover?*
-> DNS Failover is a mechanism where multiple upstream DNS servers are configured, and if the primary server becomes unavailable or fails to respond within a specified timeout, the resolver automatically switches to another DNS server.

*Why is timeout required?*
-> UDP is a connectionless protocol. When we send a DNS request, there is no guarantee that the server will respond.Without a timeout, the program would wait indefinitely for a response that may never arrive.By introducing a configurable timeout, for example two seconds, we limit how long we wait for a response. If the timeout expires, we assume the server is unavailable and automatically try the next configured DNS server.

*Why doesn't client.send() gaurantee success?*
-> client.send() only sends the UDP packet to the operating system's networking stack. It does not wait for or verify that the remote DNS server received or processed the request.A successful client.send() only means the packet has been transmitted.The actual success is determined later when the "message" event is triggered after receiving a DNS response.

*Why did you wrap socket events inside a Promise?*
-> Node.js UDP sockets are event-driven. Events like:                                                    client.on("message")                                                                                     client.on("error")                                                                                       setTimeout(...)                                                                                          occurs asynchronously.                                                                                   However, await can only pause execution for a Promise. Therefore, I wrapped the socket events inside a Promise so that await could pause until one of these events occurs. This converts callback-based asynchronous code into Promise-based asynchronous code.

*Why did you remove the outer Promise?*
-> Intially I had an outer new Promise() representing the entire forwarding operation. Later I refactored the code because an async function already returns a Promise automatically. Therefore, the outer Promise became redundant.                                                                          Instead of using: resolve(response)                          I simply used: return response;             And Instead of: reject(error)                                I used: throw error;                        The functionality remained exactly the same while making the code cleaner and more idiomatic.

*Why did you keep the inner Promise?*
-> The inner Promise is still necessary because the UDP socket API is event-based. The code needs to wait until one of these events occurs:                                                                   * response recieved                                                                                      * timeout                                                                                                * socket error                                                                                           Without wrapping these events inside a Promise, there would be nothing for await to wait for. So the inner Promise converts asynchronous events into a Promise that can be awaited.

*Difference between resolve() and return:-*
-> resolve() is used inside a manually created Promise.                                                  return is used inside an async function.                                                                 Both ultimately resolve a Promise, but return is cleaner because the async function automatically wraps the returned value inside a resolved Promise.

*Difference between reject() and throw:-*
-> reject() is used when manually creating a Promise.                                                    reject(new Error("Failed"));                                                                             Inside an async function we simply write                                                                 throw new Error("Failed");                                                                               Javascript automatically converts the thrown error into a rejected Promise.

*Why is the finished flag necessary?*
-> The timeout callback, message callback, and error callback are independent asynchronous events. There is a small possibility that two callbacks may execute almost simultaneously. Without protection, both callbacks could try to:                                                                                  * resolve the Promise                                                                                    * close the socket                                                                                       * write duplicate logs                                                                                   The finished flag ensures that only the first callback performs these operations while all subsequent callbacks immediately return.                                                                            This prevents race conditions.

*How does your DNS server recover when one upstream server fails?*
-> The DNS server iterates over the configured list of upstream DNS servers.For each server it:          1. Sends the DNS requests.                                                                               2. Waits for either:                                                                                     * response                                                                                               * timeout                                                                                                * or socket error.                                                                                       3. If a response is recieved, it immediately returns the response.                                       4. Otherwise, it moves to the next configured DNS server.                                                5. If all DNS servers fail, it throws an error indicating that every upstream server failed.

*How did you test the failover logic?*
-> I performed three tests.                                                                              Test 1:                                                                                                  Configured Google DNS as the primary server.                                                             Result:                                                                                                  The DNS request was successfully resolved.                                                               Test 2:                                                                                                  Configured an unreachable IP address as the primary DNS server and Cloudflare as the secondary server.   Result:                                                                                                  The primary server timed out after two seconds, and the request was automatically forwarded to Cloudflare. The client still received a successful DNS response.                                         Test 3:                                                                                                  Verified that the cache still functioned correctly after the refactoring and failover implementation.    Cache hits and cache misses behaved exactly as expected.

*Why did you choose UDP instead of TCP?*
-> DNS primarily uses UDP because it has lower latency and less protocol overhead. Since DNS queries are usually small request-response messages, UDP provides faster resolution.TCP is only used in situations such as:                                                                                                 * Zone transfers                                                                                         * Large DNS responses that exceed the UDP size limit                                                     * DNSSEC responses that require TCP fallback

*What is the advantage of configuration-driven design?*   
-> Instead of hardcoding values like Google DNS, I stored the upstream servers and timeout inside the configuration file.                                                                                  This allows the application to support any number of DNS servers without modifying the forwarding logic. It also improves maintainability and scalability.

*What did you learn from implementing this feature?*
-> This feature helped me understand:                                                                    * asynchronous programming using async/await.                                                           * converting callback-based APIs into Promises.                                                          * UDP socket communication                                                                               * timeout handling                                                                                       * failover mechanisms                                                                                    * configuration-driven software design                                                                   * writing cleaner production-style JavaScript through refactoring                                        * validating refactoring by testing to ensure behaviour remains unchanged
